# Friction Log — The Vak on Contentstack

| # | Step | What happened | Time lost | What Contentstack could improve for partner developers |
|---|------|---------------|-----------|--------------------------------------------------------|
| 1 | 0 — Setup | The Contentstack MCP server, Agent Skills and Vibe Docs were not configured in the local Claude Code workspace, so the AI agent could not reach the stack out of the box. | ~5 min | A single `npx` onboarding command that registers the MCP server, Agent Skills and Vibe Docs for Claude Code / Cursor in one go, with a "check connection" tool. |
| 2 | 2 — MCP setup | Global field **writes** live in the `cma-extended` group, not in `cma`, so creating the `seo`/`hero` global fields with the default `GROUPS=cma` would fail. Only found by reading the npm README. | ~5 min | Put global-field writes in the default `cma` group, or make the MCP say which group to enable when a tool is missing. |
| 3 | 2 — MCP setup | The OAuth login (`npx @contentstack/mcp --auth`) opens a browser, so an AI agent can't do it alone, and a new MCP server only loads in a new Claude Code session. | ~5 min | A device-code flow for headless agents, plus a quickstart that covers the "restart your agent" step. |
| 4 | 0 — Setup | Could not find a public "Contentstack Agent Skills" package (npm or `contentstack/agent-skills` on GitHub). | ~3 min | One canonical install link for Agent Skills and Vibe Docs on the MCP docs page. |
| 5 | 2 — MCP setup | After the restart, the MCP tools still did not show up: the API key placeholder was still in `.mcp.json`, and project-scoped MCP servers need an explicit approval in Claude Code that the desktop app did not ask for. | ~5 min | Have `--auth` offer to pick a stack and write the client config itself (API key + region), so no manual copy-paste is needed. |
| 6 | 0 — Plan check | In a new session the MCP server still failed with only `CONNECTION_CLOSED`. The real cause ("Please provide the Contentstack Stack API Key…": the key in `.mcp.json` was still a placeholder) only shows up if you run `npx @contentstack/mcp` by hand. The OAuth login had also never finished: only `{"region":"EU"}` was saved. | ~5 min | Have the server start in a degraded "setup" mode with a `whoami` / `diagnose` tool that reports a missing API key or an incomplete OAuth login, instead of exiting at startup. |
| 7 | 0 — Plan check | You can't query plan entitlements (Personalize, Lytics, Agent OS, Polaris, Brand Kit, Launch, locale and branch limits) through the MCP server. They're only shown in the Org Admin "Subscription" UI. | ~5 min | Add a read-only `get_plan_features` MCP tool, backed by the org `include_plan` API, so agents can adapt the build to the plan. |
| 8 | 0 — Plan check | The org lives on `app.contentstack.com` (AWS North America), but the MCP config and the saved OAuth state both said `EU`. Nothing warned about the mismatch, and the region isn't shown on the dashboard. On top of that, finding the stack API key from the dashboard takes several clicks (Headless CMS → stack → Settings). | ~5 min | Show the region and the stack API key, with a copy button, on the dashboard or the stack card. Have the MCP `--auth` detect the org's region and write it to the config itself. |
| 9 | 0 — Plan check | With `GROUPS` including `cda`, the server exits at startup if no Delivery token is set. On a brand-new stack you can't have that token yet, because it needs an environment, which is created in a later step. Claude Code again showed only `CONNECTION_CLOSED`. | ~5 min | Load the CDA tools lazily, or skip them with a warning when the token is missing, instead of failing the whole server. |
| 10 | 0 — Plan check | The MCP server (`cma,cma-extended`) worked first time once the config was right. But it has no tool to read the stack itself (name, settings), none to list or create **webhooks**, and none for Launch, Personalize or Brand Kit. Step 5 needs a webhook, so that part will have to go through the UI or the raw CMA. | ~3 min | Add `get_stack`, `get_all_webhooks` and `create_webhook` tools, plus `launch` and `personalize` tool groups, so the whole demo can be wired from the agent. |
| 11 | 0 — Plan check | On the trial org, Administration has no "Subscription" or "Plan & Usage" page (More → Preferences only). The only way to know which products and limits the trial includes is to open each app and check whether it loads or asks you to upgrade. | ~10 min | Add a read-only "Your plan" page to Org Admin, even for trials: product list, limits, trial end date. |
| 12 | 2 — Model | Creating a content type with a taxonomy field failed twice in a row. Each error showed only one rule at a time: first the taxonomy has to be `multiple: true` even with `max_terms: 1`, then a taxonomy can't be `non_localizable`. Neither rule is in the MCP tool description. | ~5 min | Put the taxonomy field rules (and a valid example) in the `create_a_content_type` tool description, and return every validation error at once. |
| 13 | 2 — Model | `ref_multiple_content_types: false` is silently rewritten to `true` on every single-type reference field. Harmless, but surprising when you diff exported schemas between the stacks of a site factory. | ~2 min | Keep the value that was sent, or document the normalisation. |
| 14 | 2 — Model | The MCP server has no tool to **add a locale**, **create a workflow or publish rule**, or **upload an asset**. These are three basics of a multi-market seed, so the agent has to hand over to the UI or the CLI. | ~10 min | Add `create_language`, `create_workflow` / `create_publish_rule` and `upload_asset` (from a URL or a local path) to the `cma` group. |
| 15 | 2 — Site factory | The MCP server is tied to one stack (`CONTENTSTACK_API_KEY`). A site factory (1 group stack + 3 brand stacks) needs one MCP server per stack in the config and a session restart. There's no "switch stack" tool. | ~5 min | Accept a `stack_api_key` argument per call (the OAuth token is org-wide anyway), or add a `set_active_stack` tool. |
| 16 | 2 — Workflow | In the Publish Rule form, the **Environment** field first wasn't shown, then appeared as required with "No options", although the `development` environment existed (created through the API). It worked after picking the branch / reloading the page. | ~5 min | Load environments as soon as the form opens (independent of branch), and show "No environment yet — create one" with a link instead of an empty list. |
| 17 | 2 — Site factory | `csdx cm:stacks:clone --type a` (CLI 2.0.2) **does not clone taxonomies**, then silently strips every taxonomy field from the content types ("Taxonomy 'activity' does not exist, removing from field" is only a WARN; the run reports 100% success). A full `cm:stacks:import` skipped taxonomies (0/0), environments and workflows too. Importing `--module taxonomies` only works when the `locales` export sits next to it, and re-importing `--module content-types --replace-existing` keeps stripping the fields unless the taxonomy mapper of a previous run is copied into `--backup-dir`. Clone/import also drop `_backup_*` and `logs/` folders into the current directory. | ~45 min | Include taxonomies (and publish rules) in structure clone; fail loudly instead of removing schema fields; look up existing taxonomies in the target stack instead of the run's mapper; write backups and logs to a temp dir by default. |
| 18 | 2 — Brand seed | Seeding 3 brand stacks via MCP took 45 `create_an_entry` + 36 `publish_an_entry` calls, one entry at a time: there is no bulk create or bulk publish tool, and no way to target several stacks in one call. Publishing is async (only a `job_id` comes back), and `get_publish_queue` ignores its `status` filter (`status=error` returns the same 88 successful items), so you can't ask "did anything fail?". | ~10 min | Add `bulk_publish` (entries + references, like the UI) and a `create_entries` batch tool; make `get_publish_queue` honour `status`, or add `get_publish_job(job_id)`. |
| 19 | 2 — Brand seed | Because the CLI clone dropped the publish rule (row 17), entries under the `Review` workflow were published straight from *Draft* in the brand stacks, with no warning. In a site factory that silently weakens governance on every cloned site. | ~2 min | Clone publish rules with the workflow, and warn when a workflow exists without any publish rule. |
| 20 | 3 — Front end | Neither the MCP server nor the CLI can **create a Delivery token** (`csdx auth:tokens:add` only registers an existing one). For 4 stacks I had to script the Management SDK through the CLI's internal `cli-utilities` package to reuse the OAuth session, then call a second endpoint per stack for the Preview token. | ~10 min | Add `create_delivery_token` (with `include_preview_token`) to the MCP `cma` group and a `csdx cm:stacks:tokens:create` command, so a site factory can provision every stack's front-end credentials in one step. |
| 21 | 3 — Front end | With an expired or invalid `live_preview` hash, the Delivery SDK throws (`error_code 382`, "tracker is invalid"), which fails the whole SSR page unless the app catches it. The quickstart samples don't handle it. | ~5 min | Have the SDK fall back to published content (with a warning) when the tracker is invalid, or document the fallback in the Next.js Live Preview guide. |
| 22 | 3 — Content edits | `publish_an_entry` takes `locales` as a string, but `"en-us,fr-fr,it-it,es-es"` fails with "Language doesn't exist" (error 161). Publishing 1 entry to 4 locales takes 4 calls. Updating one sentence inside a modular block also means re-sending the page's whole `sections` array. | ~5 min | Accept an array (or comma list) of locales and environments; add a field-level patch tool (e.g. JSON Patch on an entry) so small copy fixes don't rewrite whole block trees. |
| 23 | 4 — Personalize | The MCP server has no Personalize tools: the project, the custom attribute, the audiences, the experience and the link between the variant group and the `page` content type all had to be done by hand in the UI. In Personalize, the experience form never shows where content types get linked — that step lives in the CMS (Settings → Variants), which is easy to miss. | ~15 min | Add a `personalize` MCP group (attributes, audiences, experiences), and show a "Link content types in your stack" call-to-action at the end of the experience wizard. |
| 24 | 4 — Personalize | Entry variants of modular blocks: a variant can override fields of existing blocks, but reordering or removing a block/group item did not take effect on the CDA (the variant is applied, the base order stays). The MCP tool hints at `_variant._order`, but every shape tried was rejected (`errors: {_order: [""]}`) and the format isn't documented. Workaround: keep positions and swap the field values. Also, `publish_variants_of_an_entry` with a comma list of variant UIDs only published one variant, silently. | ~25 min | Document `_variant._order` with an example (and return a real validation message); accept an array of variant UIDs in the publish tool, or fail loudly when one is ignored. |
| 25 | 4 — AI translation | Publishing the fr-fr guide also published its references in fr-fr (expected), but the 3 taxonomies (activity, gender, market) failed because they only exist in en-us. The failures sit in the bulk job with a small icon; the entry itself shows "Published", so it's easy to miss. Polaris also translated title/excerpt/body but left the SEO group in English until asked. | ~5 min | Fall back to the master locale for unlocalized taxonomy terms instead of failing; surface partial failures on the entry; have Polaris' translate action cover every localizable field (groups included) by default. |
| 26 | 4 — Translations | Localizing ~50 entries into 3 locales (144 versions) is not practical through MCP (one locale per publish call, no bulk localize), so it ran as a script on the CMA. Personalize entry variants are per locale too: after the base Home page was translated, a French visitor with an affinity still got the English hero, because the en-us variant overrides the localized base. Each variant had to be localized separately (9 more versions). | ~10 min | Bulk localize/publish in MCP; warn in the entry editor when a localized base entry has variants that only exist in the master locale. |

| 27 | 5 — Launch | A trial org allows 5 Launch environments: the auto-created Compass Starter project used two, so the 4th site could not be created until it was deleted. The error said "Projects limit reached" while the dashboard showed "Environments 5/5". "Revalidate CDN cache on publish" relies on Automate, which is not in the trial, so the demo relies on ISR (60 s) instead. The deploy form also defaults to "Contentstack Authentication" on (the site needs a login) and to the deprecated Node 20. | ~15 min | Name the actual quota in the error; leave starter projects out of the trial quota; offer a built-in "revalidate on publish" toggle in Launch (no Automate needed); default to the current Node LTS. |
